High 1 issue

Screen / URL: /memberships/directory → “Add membership” dialog — https://facility-uat.quixeraos.com/memberships/directory

Steps to reproduce:

  1. Open /memberships/directory → “Add membership”.
  2. Athlete: QA Test Athlete; Plan: “12 Week — $240.00”; Facility: Cricmax Main Location; Payment: Offline/Cash → submit → toast “Session Pack plan 2 is misconfigured: no credit count”.
  3. Retry with plan “Unlimited test — $20.00” → “Record & assign” → toast “Couldn't add this membership. Please check the details and try again.”
  4. Choose Pay Later → “Assign & bill” → success “Membership assigned — $20.00 outstanding.”

Expected: A failed attempt must not persist a record; the error toast must reflect reality.

Actual: All three memberships were created — three rows for QA Test Athlete (12 Week $240, 2× Unlimited test $20); directory total 3,717 → 3,720; Active 248 → 251. Deep-dive: each “failed” attempt persisted WITH its payment record — first duplicate shows “Membership added (offline)” / “Paid off-platform” / “$240.00 · Cash · RCP-CMX-000077, Oct 10, 2026, 07:21 PM”; the Unlimited-test duplicate shows “Payment recorded $20.00 · Cash · RCP-CMX-000078” / “Membership added (offline)”. The error toasts are false negatives with full financial side effects. Worse: the row-actions menu offers only “View details” — “Freeze” and “Cancel membership” are DISABLED and no delete action exists anywhere in the UI, so the duplicates cannot be cleaned up in-app (needs backend/admin).

💡 Suggested fix: Make membership creation atomic — if validation fails, roll back; never persist on error. The “misconfigured plan” error suggests validation runs after the insert; move validation before any write or wrap in a transaction. Add a uniqueness guard (one active membership per athlete+plan), or at least surface existing memberships in the dialog. Provide an admin delete/void path for bad records.

Screen / URL: /scheduling → New Booking wizard — https://facility-uat.quixeraos.com/scheduling

Steps to reproduce:

  1. Step 1: Lane 1, Sun Oct 11, 9:00 AM, 30 min → select/create customer → step 3 → step 4 Pay Later → Create Booking.
  2. First attempt: “Failed to create booking. Please try again.” (plus “price changed to $25.00” notice).
  3. Immediate retry: “Slot just booked — This slot was just booked by someone else. Pick another slot to continue.”
  4. Different slot (9:30 AM, fresh 4:44 timer) → same conflict message.
  5. Third attempt (Lane 2, 10:00 AM) succeeded (#BK-65235).

Expected: The user's own in-progress hold must not conflict with itself; “someone else” wording only for genuine conflicts.

Actual: The failed first attempt appears to have left a hold/lock that the retry treated as another user's booking. Deep-dive: NOT reproduced in a clean run — Lane 3, Sun Oct 11, 10:30 AM succeeded FIRST TRY (“Booking Confirmed!” #BK-65236); the 9:00–9:30 AM slots show “available” on all lanes, no phantom bookings left behind. Likely the wizard collided with the tester's own prior attempt's stale slot hold. The “someone else” wording remains misleading even for genuine conflicts without attribution.

💡 Suggested fix: Tie the slot hold to the user's session — a retry from the same session should reclaim its own hold, not report a phantom conflict. On “Failed to create booking”, release the hold explicitly. Log the conflicting hold server-side so support can distinguish own-hold vs other-user conflicts; reword the message accordingly.
